10 月 28 日，我给站点调完样式，跑了一遍 `hexo g`。输出一切正常，37 个文件全部生成，没有一条报错。

打开浏览器，文章页是白的。

<!-- more -->

## 现象

`hexo g` 的日志是这样的。

```
INFO  Generated: post/54403.html
INFO  Generated: post/45351.html
INFO  37 files generated in 930 ms
```

但页面不是样式错乱，是整页空白。`view-source` 看源码，什么都没有。

```bash
$ ls -l public/post/*.html
-rw-r--r--  1 lucas  staff      0 Oct 28 23:41 45351.html
-rw-r--r--  1 lucas  staff      0 Oct 28 23:41 54403.html
```

两个文件都是 0 字节。

奇怪的是首页、归档页、标签页全都正常，只有文章详情页是空的。首页能出来，说明 markdown 渲染没问题，主题资源没缺，`_config.yml` 也没写错。问题被压缩到了 `post` 这一个布局上。

## 先排掉几个可能

按经验，其他页面正常、只有文章页空白，通常是三种情况。front-matter 解析失败，`post.pug` 里有语法错误，或者某个 helper 在渲染时抛了异常。

前两种好排。front-matter 就几行 YAML，两篇文章的头部格式一样，不可能同时坏。`post.pug` 我没动过。

只剩第三种。但 `hexo g` 从头到尾没报一个错。

## 去看视图注册表

Hexo 的布局不是从文件系统现读的。主题启动时会扫一遍目录，把找到的模板注册进 `hexo.theme.views`，结构大概是 `views.post['.pug']`、`views.index['.pug']` 这样。

如果这个表被污染了，报错不一定出现在日志里。

写个临时脚本打出来。

```javascript
// scripts/_dump.js
hexo.extend.filter.register('before_generate', () => {
  const v = hexo.theme.views;
  ['post', 'page', 'index', 'archive'].forEach(n => {
    if (v[n]) console.log(n, '=>', Object.keys(v[n]));
  });
}, 0);
```

输出是这样的。

```
post    => [ '.styl', '.pug' ]
page    => [ '.pug' ]
index   => [ '.pug' ]
archive => [ '.pug' ]
```

`post` 下面除了 `.pug`，还多了一个 `.styl`，而且它排在前面。

## 样式表怎么混进来的

`post.styl` 是主题的样式文件，实际路径 `themes/butterfly/source/css/_layout/post.styl`。

Hexo 判断「哪些文件算布局」用的是 `Pattern('layout/*path')`。`hexo-util` 3.3.0 把这个模式编译成正则时，漏了首尾锚定。

用 node 跑一下就看得出来。

```javascript
const Pattern = require('hexo-util').Pattern;
const p = new Pattern('layout/*path');

p.match('layout/post.pug');                  // { path: 'post.pug' }
p.match('source/css/_layout/post.styl');     // { path: 'post.styl' }  ← 命中了
p.match('source/css/_styles/post.styl');     // undefined
```

本来应该只认以 `layout/` 开头的路径。锚定一丢，就变成了「路径里包含 `layout/` 就行」。

`_layout/post.styl` 里有 `layout/post.styl` 这一段，命中。

## 名字是怎么撞上的

关键在这里。因为匹配是从 `_layout/` 中间开始的，`params.path` 只拿到了 `layout/` 后面那一截，也就是 `post.styl`，前面的 `source/css/_` 全丢了。

`setView` 再按「去掉扩展名当视图名」的规则处理，得到名字 `post`、扩展名 `.styl`。

而 `layout/post.pug` 走同一条路，名字也是 `post`，扩展名 `.pug`。

两个文件挤进了同一个桶。

```javascript
views.post = {
  '.styl': <post.styl 编译出来的东西>,
  '.pug':  <真正的模板>
}
```

`.styl` 排前面，是因为主题的处理器顺序是 `[config, i18n, source, view]`，`source` 先扫 `source/` 目录，`view` 后扫 `layout/`。

渲染文章时，`getView('post')` 取的是 `Object.keys()` 的第一个，也就是 `.styl`。

于是 Hexo 拿一份 stylus 样式表当 pug 模板去渲染。编译器读不懂，报错，落盘的就是空文件。

## 为什么只有文章页坏了

因为 `_layout/` 目录里恰好有 `post.styl`，没有 `page.styl`。

```
aside.styl    chat.styl      comments.styl   footer.styl
head.styl     loading.styl   pagination.styl post.styl
relatedposts.styl            reward.styl     rightside.styl
sidebar.styl  third-party.styl
```

`page`、`index`、`archive` 这些名字没被占用，`views.page` 下面还是只有 `.pug`，所以页面页、首页、归档页都正常。

同样的道理，如果 Butterfly 当初把样式目录命名成 `_styles` 或者 `_css`，这个 bug 根本不会出现。反过来说，换主题也未必安全，只要主题的 source 目录里有一层叫 `_layout` 的文件夹，就会踩上。

## 修复

布局只能是模板文件，把误注册进来的样式后缀清掉就行。

```javascript
// scripts/fix-theme-views.js
hexo.extend.filter.register('before_generate', () => {
  const views = hexo.theme && hexo.theme.views;
  if (!views) return;

  const STYLE_EXTS = ['.styl', '.stylus', '.css', '.scss', '.less'];

  Object.keys(views).forEach(name => {
    const byExt = views[name];
    if (!byExt) return;

    STYLE_EXTS.forEach(ext => {
      if (byExt[ext]) delete byExt[ext];
    });

    if (Object.keys(byExt).length === 0) delete views[name];
  });
}, 1);
```

最后那个 `1` 是优先级，数字小的先执行，保证在生成之前清完。

脚本放 `scripts/` 而不是直接改主题，理由有两个。主题是 submodule，改了下次 `git submodule update` 就没了。另外 Hexo 会自动加载 `scripts/` 下所有 js，CI 构建时同样生效，本地和线上行为一致。

## 验证

重新生成，看文件大小。

```bash
npx hexo g
ls -l public/post/*.html
```

有内容就算过。顺手再打一次视图表，`post` 下面应该只剩 `.pug`。

## 上游的情况

`hexo-util` 3.3.0 有这个毛病，4.0.0 也没修。Hexo 7.3.0 和 8.1.2 都会中招。

```bash
npm ls hexo-util
```

哪天上游补了锚定，这个脚本删掉也不影响，它只做清理，不改正常流程。

真正卡住的不是修，是定位。从头到尾 `hexo g` 都说成功，37 个文件全生成了。加上 `--debug` 才看到一行 `ERROR Render HTML failed: post/54403.html`，没有堆栈，也没说是哪个文件出了问题。

等看到 `views.post` 下面挂着 `.styl`，剩下的十分钟就修完了。

所以以后再遇到「构建成功但产物是空的」，我会先去翻视图注册表，而不是怀疑 markdown。
