## 关于本站

站名「风月酌酒」，取自"风月"与"酌酒"——看风景，喝点酒，顺便写点东西。

内容主要分四块：

- **编程**：学习笔记、踩坑记录、工具折腾
- **动漫**：看过的番、偶尔的感想
- **游戏**：玩过的东西
- **生活**：没什么主题的随笔

这里不是教程站，更像是自己的一个数字花园。写下来的东西首先是给自己看的，如果恰好对别人有用，那就更好了。

## 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 生成器 | Hexo 7.3 | 纯静态输出，没有数据库和后台，托管成本几乎为零 |
| 主题 | Butterfly 5.7 | 卡片式布局，功能齐全，社区活跃 |
| 部署 | GitHub Pages + Actions | 推代码即发布，不用买服务器 |
| 搜索 | hexo-generator-search | 本地搜索，不依赖第三方服务 |
| 评论 | 暂未启用 | 先用 GitHub / 邮箱联系 |

选静态站的核心原因很简单：写博客这件事本身已经够费劲了，不想再维护一台服务器。

## 从零搭建

### 1. 准备环境

```bash
node -v          # 建议 20 或 22 的 LTS 版本
git --version
```

Node 版本别太新。Hexo 7 发布较早，用最新的 Current 版本偶尔会遇到依赖不兼容，LTS 最稳。

### 2. 初始化 Hexo

```bash
npm install -g hexo-cli
hexo init blog
cd blog
npm install
```

### 3. 引入主题

Butterfly 用 git submodule 引入，这样主题可以独立更新，不会和自己的配置混在一起：

```bash
git submodule add https://github.com/jerryc127/hexo-theme-butterfly.git themes/butterfly
git submodule update --init --recursive
```

然后改两处：

```yaml
# _config.yml
theme: butterfly
```

```bash
# 把主题自带配置复制到根目录，之后只改根目录这份
cp themes/butterfly/_config.yml _config.butterfly.yml
```

这一步很关键：`_config.butterfly.yml` 放在根目录，主题目录保持干净。以后 `git submodule update` 拉新版本，配置不会丢。

### 4. 关键配置

**固定短链接**。Hexo 默认用标题生成 URL，改标题链接就变了，外部引用全断。用 `hexo-abbrlink` 生成固定 ID：

```bash
npm install hexo-abbrlink --save
```

```yaml
# _config.yml
permalink: post/:abbrlink.html
abbrlink:
  alg: crc32   # crc16 或 crc32
  rep: hex     # dec 或 hex
```

这样每篇文章的链接在第一次生成时就定下来了，之后改标题也不影响。

**本地搜索**：

```bash
npm install hexo-generator-search --save
```

```yaml
# _config.yml
search:
  path: search.xml
  field: all
  content: true
```

```yaml
# _config.butterfly.yml
search:
  use: local_search
  placeholder: 搜索文章
```

### 5. 本地预览

```bash
npx hexo clean && npx hexo generate
npx hexo server -p 4000
```

打开 <http://localhost:4000> 就能看到。`hexo server` 会监听文件改动，改完自动重新生成。

### 6. 部署到 GitHub Pages

站点分两个仓库：

- **源码仓库**（`blog`）：Hexo 源文件，日常写文章推这里
- **产物仓库**（`<用户名>.github.io`）：构建出的 `public/`，Pages 从这里读

用 GitHub Actions 串起来，`.github/workflows/deploy-pages.yml` 大致流程：

1. `actions/checkout` 拉源码，注意要带 `submodules: recursive`，否则主题目录是空的
2. `actions/setup-node` 装 Node
3. `npm ci && npm run build`
4. 通过 Deploy Key 把 `public/` 推到产物仓库

认证方式上，用 **Deploy Key** 比 PAT 省心：一次配好、不会过期、不用纠结 token 作用域。

```bash
ssh-keygen -t ed25519 -C "deploy-key@example.github.io" -f .deploy-key/id_ed25519 -N ""
```

- 公钥 → 产物仓库的 Settings → Deploy keys，**务必勾选 Allow write access**
- 私钥 → 源码仓库的 Settings → Secrets → Actions，命名为 `DEPLOY_KEY`

## 目录结构

```text
blog/
├── _config.yml              # Hexo 主配置
├── _config.butterfly.yml    # 主题配置（与主题源码分离）
├── source/
│   ├── _posts/              # 文章
│   ├── _data/link.yml       # 友链数据
│   ├── css/custom.css       # 自定义样式
│   └── js/universe.js       # 夜间星空特效
├── themes/butterfly/        # 主题（git submodule）
├── scripts/                 # 自定义 Hexo 脚本
└── .github/workflows/       # 自动部署
```

## 为什么自定义样式要单独放

主题目录是 submodule，**任何直接改动都会在下一次更新时被覆盖**。所以样式一律写在 `source/css/custom.css`，通过 `_config.butterfly.yml` 的 `inject.head` 注入：

```yaml
inject:
  head:
    - <link rel="stylesheet" href="/css/custom.css">
```

它加载在主题的 `index.css` 之后，同优先级下就能覆盖主题样式，升级主题也不会丢改动。

夜间星空效果同理，`source/js/universe.js` 是一个 canvas 粒子脚本，只在 `data-theme="dark"` 时绘制，切回白天会清空画布——这样日夜切换不会有残留。

## 常见问题

### 克隆后页面全白

九成是主题没拉下来。`themes/butterfly` 是 submodule，普通 `git clone` 不会自动拉取：

```bash
git submodule update --init --recursive
```

### 样式或图片 404

检查 `_config.yml` 里的 `url`。部署到 GitHub Pages 时如果站点在子路径下，还要确认 `root` 配置，否则所有绝对路径都会错位。

### 改了标题，链接变了

说明没启用 `abbrlink`。启用后链接由 `abbrlink` 字段决定，和标题解耦。**已经发布的文章不要随意改 `abbrlink` 的值**，那等于换了链接。

### 文章页空白，生成的文件是 0 字节

这个坑比较隐蔽。Hexo 用 `Pattern('layout/*path')` 识别主题布局，而 `hexo-util` 3.3.0 的 `Pattern` 编译正则时没有加首尾锚定，导致只要路径里出现 `layout/` 子串就会命中。

Butterfly 的样式目录 `themes/butterfly/source/css/_layout/` 正好踩中，于是 `post.styl`、`sidebar.styl` 这些样式表被注册成了同名布局，把真正的 `post.pug` 覆盖掉。文章页拿样式表当模板渲染，自然报错、输出空文件。

修复方式是在站点根目录加一个 `scripts/` 脚本，生成前把误注册的样式视图剔掉：

```javascript
// scripts/fix-theme-views.js
hexo.extend.filter.register('before_generate', () => {
  const views = hexo.theme && hexo.theme.views;
  if (!views) return;

  const STYLE_EXTS = ['.styl', '.stylus', '.css', '.scss', '.less'];

  Object.keys(views).forEach(name => {
    const byExt = views[name];
    if (!byExt) return;

    STYLE_EXTS.forEach(ext => {
      if (byExt[ext]) delete byExt[ext];
    });

    if (Object.keys(byExt).length === 0) delete views[name];
  });
}, 1);
```

布局本来就只能是模板文件，所以移除这些样式视图是安全的。放在 `scripts/` 而不是改主题，是为了 CI 构建时同样生效。
